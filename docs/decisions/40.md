# Log de Decisões — Issue #40: Aguardar Quota do Escalador

## DOR → SPEC — 2026-09-26

- **Decisão:** Aceitar a spec da issue como suficiente; não há ambiguidade nos requisitos e o contrato 429 já foi definido no backend#64.
- **Risco aceitado:** Dependência no contrato `{ code: "optimization_quota_exceeded" }` — se o backend mudar o campo `code` ou `Retry-After`, o frontend não reconhecerá e tratará como erro normal (comportamento gracioso, sem falha).

## SPEC → PROMPT PLAN — 2026-09-26

- **Decisão:** Usar AbortController + fake timers (vitest) para testes — permite controle total sobre timing sem sleeps reais e garante cleanup em unmount.
- **Decisão:** Congelar parâmetros (orçamento, esquema, modo) durante retry em vez de permitir mudanças — reduz ambiguidade de "qual requisição repetir?" se o usuário alterar enquanto aguarda.
- **Risco aceitado:** Usuário quer mudar parâmetros durante retry → precisa cancelar primeiro; isso é aceitável porque a espera é curta (tipicamente < 10s) e o botão "Cancelar" deixa claro o que fazer.

## PROMPT PLAN → TDD — 2026-09-26

- **Decisão:** Implementar máquina de estados simples (idle, loading, waiting_retry) em vez de library (xstate) — isola lógica sem dependência extra; clareza prevalece sobre escalabilidade hipotética.
- **Decisão:** Usar relógio fake (`vi.useFakeTimers()`) nos testes — garante controle determinístico e evita flakiness por timing; respeita a prática do projeto (ver testes existentes).
